1 · The idea

Closed-book exam vs open-book exam

Closed book

The model alone

Answers from memory. It has never seen your handbook, your notes or last week's news, so it guesses in a confident voice.

Open book

The model + the right page

Before answering, we look up the relevant page and put it on the desk. Now it only has to read and explain.

Retrieval-Augmented Generation: retrieve the right pieces of your documents, augment the prompt with them, let the model generate the answer.
1 · The idea

The whole system on one slide

Two lanes. Press → to walk through them.

Chunking. Cut the documents into pieces small enough to send to a model.

Embedding + indexing. Turn each piece into numbers that capture its meaning, and store them so they are quick to search.

Retrieval. Find the chunks whose numbers are closest to the question's.

Augmentation. Paste those chunks into the prompt, next to the question.

2 · Chunking · watch it fail

Why not paste the whole handbook into every prompt?

  • It may not fit. Our toy FAQ is 16 lines. A real handbook is 300 pages, a company wiki is millions.
  • You pay and wait for every word, on every question. Even when the answer is one sentence.
  • Needles get lost in haystacks. The more unrelated text around the answer, the more often models miss it.
Predict
So we cut the document into chunks and send only the useful ones. How big should a chunk be: a sentence, a paragraph, a page? What goes wrong at each extreme?

2 · Chunking · code

Recursive splitting is one library call

from langchain_text_splitters import RecursiveCharacterTextSplitter

def make_splitter(size=300, overlap=50):
    return RecursiveCharacterTextSplitter(
        chunk_size=size,                    # the longest a chunk may be, in characters
        chunk_overlap=overlap,              # how much two neighbours share
        separators=["\n\n", "\n", ". ", " ", ""],   # biggest break first
        keep_separator="end")               # a full stop stays with its sentence

pieces = make_splitter(200, 0).split_text(text)

Press → to step through the code.

The library. LangChain ships the algorithm you just watched. You do not write the splitting yourself.

Size and overlap. The same two dials as in the first demo: the most characters a chunk may hold, and how much two neighbours repeat.

The separators. The list from the demo, from the biggest break to the smallest: blank line, line break, full stop, space, and finally "anywhere".

Where the separator goes. "end" keeps each full stop attached to the sentence before it, so chunks do not start with a stray dot.

Use it. A list of strings comes back. In Part 7 your own PDF is cut with this function.

3 · Embeddings · code

Embed once, compare with a dot product

from sentence_transformers import SentenceTransformer
embedder = SentenceTransformer("all-MiniLM-L6-v2")     # small, free, runs on a laptop

def cosine(a, b):
    return a @ b / (np.linalg.norm(a) * np.linalg.norm(b))

emb = embedder.encode(texts, normalize_embeddings=True)
emb.shape                                              # (47, 384)

Press → to step through the code.

The model. The same one that drew the map on the last slide. It is 90 MB and needs no API key.

Cosine similarity. The dot product a @ b divided by both lengths np.linalg.norm(a), np.linalg.norm(b).

Embed every chunk once. One row per chunk. normalize_embeddings=True makes every length 1, so from here on cosine similarity is a plain dot product. That is what the vector index in the next part computes.

The trick

Group similar vectors into clusters ahead of time. For a question, find the nearest cluster centres and search only inside those.

Like going to the right shelf in a library instead of reading every spine.

4 · Vector index · the kinds

A vector index answers one question: which stored vectors are nearest?

Flat

Compare with every vector. Always exact. Fine for thousands of chunks, and what your Colab uses.

Clusters (IVF)

Search only inside the nearest clusters. Much faster, can miss. The demo you just played.

Graph (HNSW)

Hop along links between neighbours toward the question. Fast and accurate, uses more memory. The default in most vector databases.

index = faiss.IndexFlatIP(384)           # an empty index for 384-number vectors
index.add(emb)                           # store every chunk's vector
scores, ids = index.search(q, 3)         # ask for the 3 chunks nearest to the question

A vector database (Chroma, Qdrant, pgvector) is an index like these, plus storage on disk, filters and updates.

5 · Hybrid search · code

BM25 for keywords, rank fusion to combine

bm25 = BM25Okapi([tokenize(t) for t in texts])        # count words in every chunk
scores = bm25.get_scores(tokenize(question))          # rare matching words score high

def rrf(rankings, k=60):
    points = {}
    for ranking in rankings:                          # one ranked list per search method
        for rank, i in enumerate(ranking, start=1):
            points[i] = points.get(i, 0) + 1 / (k + rank)
    return sorted(points.items(), key=lambda item: -item[1])

Press → to step through the code.

BM25. A chunk scores when it contains the question's words. A rare word such as b-204 counts far more than a common one such as room.

Two lists in. BM25 scores (0 to 10) and cosine scores (0 to 1) cannot be added. So we throw the scores away and keep only the positions.

Reciprocal rank fusion. Position 1 earns 1/61, position 2 earns 1/62, and so on. A chunk that is near the top of both lists collects the most points.

Sort by points. That is the whole algorithm, and it is what many production search systems use.

6 · Generation · code

The last two functions: your RAG is complete

def build_prompt(question, results):
    context = "\n".join(f"[{chunks[i]['id']}] {chunks[i]['text']}" for i, _ in results)
    return f"""You are a helpful assistant for Moghazy University students.
Answer the question using ONLY the context below.
If the answer is not in the context, say "I don't know based on the handbook."
Cite the chunk ids you used in square brackets, like [c12].
Context: {context}
Question: {question}"""

def rag(question, k=3):
    results = hybrid_search(question, k)                 # retrieve
    return ask_llm(build_prompt(question, results))      # augment + generate

Press → to step through the code.

Context. One line per retrieved chunk, each starting with its id so the model can cite it.

Rules. Stay inside the context, admit when the answer is missing, say where the answer came from.

The open book and the question. This is the "augmented" in RAG: plain text pasted into a prompt.

Three lines for the whole system: retrieve, augment, generate.

7 · Failure clinic

Three broken RAGs. Which part do you fix?

Case 1. "What is the late penalty?" → "You lose 10% per day." It never mentions the zero after five days. The retrieved chunk ends in the middle of a sentence.

The fact was split across two chunks. Split at paragraph boundaries or add overlap.

Case 2. "What is room B-204 used for?" → a confident answer about room B-240. The B-204 sentence is not among the retrieved chunks.

The right chunk was never retrieved. Add keyword search and fuse the rankings.

Case 3. "How much is a parking permit?" → "A permit costs 50 lumens per semester." The handbook has no parking section.

Nothing to retrieve, so the model filled the gap. Tell it to answer only from the context and to say when it does not know.

8 · RAG vs long context

Some models now read a million tokens at once. Is RAG still needed?

RAG

Select, then read

Chunk, embed, index, search. Send the model a few passages.

What you built today.

Long context

Read everything, every time

No chunks, no embeddings, no index. Paste all the documents into the prompt and let the model find the answer.

A million tokens is roughly 700,000 words: several long novels.

Our whole handbook is about 2,500 tokens. It fits in any model, hundreds of times over. So was today a waste? Two views coming up.
8 · RAG vs long context

Three points each way

For long context
Far fewer moving parts. No chunking strategy, embedding model, vector store or sync job to break.
No retrieval misses. RAG can fail silently: the answer was in the data, but search never showed it to the model.
Whole-document questions. "What is in the requirements but missing from the release notes?" needs both documents in full, not a few snippets.
For RAG
No re-reading. Long context processes every document again on every question. RAG pays once, at indexing time. Caching helps when the documents rarely change.
Less noise. Models can miss a detail buried deep inside a huge prompt. A handful of relevant chunks keeps the model on the signal.
Data bigger than any window. A company's documents are measured in terabytes. Something has to choose what goes in.

Summarised from Martin Keen, "Is RAG Still Needed? Choosing the Best Approach for LLMs", IBM Technology (YouTube, 2026).

The prompt starts exactly like the last one, so only the new question is read.

Someone added today's date at the top. The prompt no longer starts the same, so nothing can be reused.

Keep the start identical. Instructions and documents first, the question last. Anything that changes goes at the end.
It does not last. The saved work is kept for minutes to hours, so it pays off when questions come often.
It saves money and time, not attention. The model still looks across every document, so a detail buried in a huge prompt is as easy to miss as before. And the documents still have to fit in the window.
8 · RAG vs long context

So which one? Ask four questions about your problem

Lean to long context when
  • the documents are few and bounded (one contract, one book)
  • the question needs the whole text: summarise, compare, find what is missing
  • questions are rare, or the text is stable enough to cache
Lean to RAG when
  • the data is larger than the window, or keeps growing
  • questions are lookups: one fact, one rule, one page
  • many people ask, all day: cost and waiting time add up
  • you must show the source of every answer
In practice it is often both: retrieve generously, then give a long-context model whole sections instead of tiny snippets. Retrieval decides what the model reads; the window decides how much.
